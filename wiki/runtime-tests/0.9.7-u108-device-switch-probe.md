## Purpose

The story proposed two toggles from the open-revo registry
(`open-revo\src-tauri\config\ec_registry.json`): AC power recovery
`ADDR_AC_RECOVERY = 1830 (0x0726)` with `AC_RECOVERY_BITMASK = 8`, and
"win-key lock" at `ADDR_FN_LOCK = 1870 (0x074E)`. Reading open-revo's own
driver (`src\driver\wmi_ec.rs`, `src\system\switches\mod.rs`) shows the
registry conflates two distinct switches: `0x074E!bit4` is the **Fn-key
lock** (RMW `| 0x10`), while the **Win-key lock** is a status/trigger pair —
`ADDR_STATUS_BYTE 1896 (0x0768)!bit0` read, `ADDR_TRIGGER_BYTE 1895
(0x0767) |= 1` fired — with **no write-the-state primitive at all**. Both
switches ship; the probe's job was to establish on THIS chassis: (1) the
`0x0726!bit3` write coexists with UCU's power-management handshake at
`bit7` of the same byte (story acceptance b), (2) `0x074E!bit4` is writable
here, (3) what firing `0x0767` actually does.

## Method

`docs\acpi\SwitchDiagnostic` opens `\\.\ACPIDriver` (`IOCTL_ECREAD
0x9C40A488` / `IOCTL_ECWRITE 0x9C40A48C`) and **toggles one bit at a time,
then restores the byte it read** — reversible by construction — with
readback checks (bit moved? other bits preserved? protected bit preserved?).
The Win-lock test fires the trigger and polls `0x0768` for the flip. Run
elevated:

```powershell
dotnet build docs\acpi\SwitchDiagnostic -c Release
Start-Process powershell -Verb RunAs -WindowStyle Hidden `
  -ArgumentList "-NoProfile -Command `"& '<...>\SwitchDiagnostic.exe' > '<out>.txt' 2>&1`""
```

## Observed (lab box, 2026-10-31)

Baseline: `0x0726 = 0x80` (handshake gate set, recovery off),
`0x074E = 0x01` (Fn unlocked), `0x0765 = 0xE1`, `0x0766 = 0x10`,
`0x0767 = 0x00`, `0x0768 = 0x00` (Win unlocked).

```
--- AC_RECOVERY: toggle 0x0726 bit mask 0x08 ---
  read:    0x80  (bit set: False)
  after:   0x88  bit moved: YES  other bits preserved: YES
  power-mgmt bit7 preserved: YES
  restored: 0x80 == original 0x80: PASS

--- FN_LOCK: toggle 0x074E bit mask 0x10 ---
  read:    0x01  (bit set: False)
  after:   0x11  bit moved: YES  other bits preserved: YES
  restored: 0x01 == original 0x01: PASS

--- WIN_LOCK: status 0x0768 bit 0, trigger 0x0767 |= 0x01 ---
  trigger: 0x00  status: 0x00  win-locked: False
  after fire #1: status 0x01  win-locked: True  flipped: YES
  after fire #2: status 0x01  win-locked: True  restored: FAIL   <- debounce
  trigger byte at end: 0x00 (bit0 self-consumed: YES)
```

The fire-#2 miss was chased by `docs\acpi\WinLockProbe`:

```
start: 0x0768=0x01 0x0767=0x00 0x074E=0x01 locked=True   <- persisted across processes
  [fire RMW (0x0767|=0x01)] t+0.1s 0x0768=0x00 FLIPPED (locked now: False)
final: 0x0768=0x00 locked=False
OUTCOME: win-key UNLOCKED.
```

A fire ~0.2 s after the previous fire was swallowed; a fire seconds later
flipped the state back within ~0.1 s. The lock state is EC-owned: a fresh
process saw the locked byte the previous run left behind. The machine was
left UNLOCKED.

## Verdict

1. **AC recovery ships as a bit-scoped RMW on the shared byte.** `0x0726!bit3`
   is writable and a bit-3 write leaves bit 7 (the handshake's
   power-management gate) and every other multiplexed bit untouched —
   acceptance (b) observed live, not just pinned in tests. `0x0726` keeps
   exactly one discipline: every writer (the handshake's `| 0x80`, the
   stock-mode clear, the recovery toggle) touches only its own bit, and the
   engine's single serialized power-domain queue orders them.
2. **Fn lock is writable here with the open-revo encoding** (`0x11` locked /
   `0x01` unlocked), plain bit-scoped RMW, preserves the rest of the byte.
3. **Win-lock SET is a fire, not a write.** The truth is `0x0768!bit0`;
   arming `0x0767!bit0` TOGGLES the lock, self-consumes, reacts in ~0.1 s,
   and a re-fire inside the firmware's debounce window is swallowed. The
   engine's shape follows the evidence: fire ONLY on truth mismatch (a
   fire-on-match would toggle AWAY from the target), exactly once per
   command, verify by re-read, and the SET verb answers with the **observed**
   EC state — a swallowed fire shows up as `false`, never as a silent
   success.
4. **State persistence is EC-side** (acceptance a): the lock survived across
   probe processes, so the app never re-applies on startup — it re-reads.
5. The support lineage `0x0765/0x0766` (`0xE1`/`0x10`) is recorded as
   context. The per-bit semantics on this chassis are NOT claimed, so row
   visibility gates on version skew (`UnsupportedVerb`) and EC availability,
   not on decoded support bits — the U-103/U-107 evidence-first rule.

## Acceptance mapping (story U-108)

| Criterion | Result on the lab box |
|---|---|
| (a) win-lock toggle round-trips and survives app restart | fire → flip verified by re-read (Hardware sim + Engine wire tests); persistence proven by the EC-side status byte observed across processes; the page re-reads truth at construction |
| (b) ac-recovery round-trips, handshake bit untouched | probe PASS above; golden writes `0x80→0x88` / `0x91→0x99` pinned (Hardware), exhaustive 256-byte preserve-all-other-bits sweep pinned (Core), wire golden pinned (Engine) |
| (c) capability-unsupported → rows hidden | rows default Collapsed; shown only after a successful truth read; pre-U-108 engine answers `UnsupportedVerb` → hidden, mid-session engine swap → hidden on actuation |

## Deviations from the story

- The story's title ("Win-key lock") mapped `ADDR_FN_LOCK` to the Win key;
  open-revo's driver shows they are two switches. **Both ship**:
  `keyboard.get/set_win_lock` (status/trigger) and
  `keyboard.get/set_fn_lock` (bit RMW).
- Win-lock SET is trigger-toggle + verify, not a state write (the register
  cannot be written to a state).
- SET verbs answer with the observed EC state, not the request.
- Capability gating is `UnsupportedVerb` version skew + EC availability, not
  the story's "support bytes 1893/1894" (per-bit semantics unprobed here).
- The AC-recovery verb rides the **power** domain (ordering against the
  handshake's RMWs on the shared byte); the win-lock verb rides the
  **keyboard** domain (ordering against the lighting-effect writes on the
  shared trigger byte).
