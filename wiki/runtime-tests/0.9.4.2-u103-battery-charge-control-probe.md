## Purpose

The OpenRevo port story proposed battery charge control from a **foreign chassis registry**
(`open-revo\src-tauri\config\ec_registry.json`): modes `0x01/0x11/0x21`, an explicit
threshold pair on `0x07C9`/`0x07D0`, a gate bit on `0x0742!bit4`, a platform-override byte
on `0x0770` (pin `5`, reset `0xFF`). UCU's shipped `EcBatteryCodec` decodes `0x07A6` with a
**different encoding** (field bits 3-5, mask `0x38`, values `0x08/0x18/0x28` = 100/80/60 %).
The story's own risk note made the lab-box probe the gate for enabling anything: the two
encodings claim the same bit 3 for different things.

## Method

`docs\acpi\BatteryDiagnostic` opens `\\.\ACPIDriver` (`IOCTL_ECREAD 0x9C40A488`) and reads —
no writes — the whole battery-control family plus a neighborhood scan, decoding `0x07A6`
for BOTH chassis families side by side and cross-checking plausibility (SOC, capacities,
power source). Run elevated:

```powershell
dotnet build docs\acpi\BatteryDiagnostic -c Release
Start-Process powershell -Verb RunAs -WindowStyle Hidden `
  -ArgumentList "-NoProfile -Command `"& '<...>\BatteryDiagnostic.exe' > '<out>.txt' 2>&1`""
```

## Verdict

1. **The lab box speaks the UCU encoding family.** `0x07A6 = 0x28` decodes cleanly as
   Stationary (60 %) through the shipped codec; it matches **no** open-revo mode byte.
   The legacy 100/80/60 UI path stays exactly as shipped.
2. **The open-revo threshold registers are refuted on this chassis.** `0x07C9 = 0` and
   `0x07D0 = 95` are not a percent pair (the registry's own validation `60..100, down<up`
   fails). So UCU ships **no threshold write path**: writing unverified addresses against
   an EC-proprietary layout is exactly the brick vector the evidence-first rule exists for.
   The threshold pair the UI shows is the **mode's ceiling plus hysteresis** (`limit-5`,
   the open-revo driver convention), derived in `EcBatteryCodec.ThresholdsForMode` and
   pinned by tests — a presentation of verified state, not a second control path.
3. **The gate byte is readable and multiplexed.** `0x0742!bit4` is UCU's fan-turbo support
   bit on fan rows and OpenRevo's "gate active" bit on battery rows; the lab box idles at
   `0x02` (bit4 clear, charging at 99 % on AC). The Battery page renders it as a live
   status row (5 s poll) and never writes it.
4. **The platform-override byte idles at the documented reset (`0xFF`).** The row is a
   notice, shown only when a firmware-side or third-party tool has pinned it; the EC then
   applies charge modes non-naively and the page says so.
5. `0x0770` neighborhood reads `FF…` with a `55 AA` marker at `0x077E/0x077F` — layout
   context captured for the next probe; no semantics claimed.

## Acceptance mapping (story U-103)

| Criterion | Result on the lab box |
|---|---|
| (a) mode read/write round-trips on supported ECs | yes — codec round-trip pinned (Core), golden write pinned (Hardware), wire round-trip pinned (Engine) |
| (b) threshold pair validated (down<up, 60..100) | codec-level `ValidateThresholds` pinned; **no write surface on this family** (refuted registers), so no EC-facing BadRequest path |
| (c) gate status renders live (5 s poll kept) | three new read verbs + page row on the existing 5 s timer |
| (d) unsupported chassis → rows hidden | an engine predating the verbs answers `UnsupportedVerb` and the rows hide; EC-absent state keeps the existing unavailable card |
| (e) legacy 60/80/100 UI path unchanged | unchanged (probe confirms the codec's live decode) |
