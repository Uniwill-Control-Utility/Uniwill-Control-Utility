## Startup observations

### Time to the first visible window

One normal launch reached a visible, responding main window after approximately `9.63 s` from process creation. The saved configuration contained `StartMini=True`, so later launches continued in the tray and could not be evaluated by waiting for a persistent visible window.

A managed stack captured during a tray-start run showed the main WPF thread waiting normally in `Dispatcher.GetMessage`. It did not show a dispatcher deadlock. The process already had 63 managed/native threads after startup.

### First launch from a new application directory

When the executable path changed to the Debug output directory, startup executed `App.UnblockFilesInDirectory`. The directory contained 135 top-level files. The implementation launched one PowerShell process per file through `Parallel.ForEach`.

All 135 invocations failed because the application path contains spaces and the generated command was parsed as multiple arguments:

```text
Unblock-File : A positional parameter cannot be found that accepts argument 'Control'.
```

Measured output:

| Metric | Result |
|---|---:|
| Top-level files processed | 135 |
| PowerShell command failures | 135 |
| Captured standard-error size | 62,358 bytes |

Relevant source path:

```text
App.OnStartup
  -> Task.Run(UnblockFilesInDirectory)
     -> Parallel.ForEach(Directory.GetFiles(path))
        -> Start powershell.exe for each file
```

This path adds process creation, PowerShell initialization, file enumeration, and error output to a new-directory startup. Redirected standard error is not consumed by `UnblockFile`, while only standard output is drained.

## Sensor pipeline findings

### Current shared service

`HardwareMonitoringService` shares one LibreHardwareMonitor `Computer` instance and suppresses repeated hardware-tree updates within 250 ms. This is a short time gate, not a producer-side sample cache:

```text
consumer calls ReadSnapshot
  -> acquire global service lock
  -> update every enabled hardware node if 250 ms elapsed
  -> enumerate sensor trees repeatedly by name
  -> read memory and storage data
  -> build and return a new snapshot
```

The application acquires a persistent lease for CPU, GPU, memory, and battery before showing the main window. `HardwareMonitoringService` additionally enables motherboard, storage, and controller monitoring for every non-empty category set. Consequently, CPU-temperature-only consumers keep the wider hardware inventory open and update the full tree.

### Blocking dispatcher paths

Two one-second WPF `DispatcherTimer` callbacks perform direct reads:

1. `DashboardViewModel.OnRefreshTimerTick` calls `ReadSnapshot` and then performs two EC fan-PWM reads on the UI thread.
2. `FanControl.StatusTimer_Tick` calls `ReadSnapshot`, waits up to 500 ms for an EC semaphore on the UI thread, and then performs two EC fan-PWM reads.

If a driver, storage probe, GPU API, or EC call is slow, the WPF message loop cannot render or process input until that callback returns.

### Duplicate and phase-dependent reads

Background consumers include the performance overlay, EC smart fan control, two Flydigi smart-control loops, Hydro UI smart mode, and the Flydigi page temperature display. Their default intervals range from one to two seconds.

`FlydigiTemperatureProvider.GetMaxTemperature` calls `GetCpuTemperature` and `GetGpuTemperature`; each creates a complete `HardwareMetricsSnapshot`. The 250 ms update gate usually avoids a second hardware-tree update, but snapshot construction and sensor enumeration still happen twice.

Multiple independent timers can drift more than 250 ms apart. In that case each consumer can trigger a separate full hardware-tree update even though all consumers need substantially the same readings.

### Overlay behavior

`PerformanceOverlayViewModel` moves `ReadSnapshot` to `Task.Run` and refreshes hardware data once per second. However, its WPF timer can run as frequently as every 16 ms and updates many properties on each tick. This is separate from hardware I/O and should be measured when the overlay is enabled.

## Windows 10 navigation icon finding

The Windows 10 test host does not contain the `Segoe Fluent Icons` font. It contains `Segoe MDL2 Assets`.

`MainWindowViewModel.createNavItem` assigns every ordinary navigation section a `FontIcon` whose font family is explicitly `Segoe Fluent Icons`. Missing glyphs therefore render as square placeholders on this operating system. The project already uses `Wpf.Ui.Controls.SymbolIcon` for other controls and path-based icons for the Flydigi and fan entries, so the existing bundled/icon-control approach can replace the operating-system font dependency without changing navigation layout.

This finding is based on the Windows font inventory and the actual navigation construction code. The test automation did not capture a UI screenshot.

## Confirmed issues and priorities

1. **New-directory startup:** one PowerShell process per output file, incorrect argument parsing for paths with spaces, and undrained standard error.
2. **UI-thread hardware I/O:** dashboard and fan-control dispatcher callbacks directly call LibreHardwareMonitor and EC methods.
3. **Polling ownership:** multiple independent timers request overlapping data from the same service.
4. **Over-broad sampling:** storage, motherboard, and controller monitoring are enabled even for narrow CPU/GPU requests.
5. **Snapshot duplication:** `GetMaxTemperature` builds two full snapshots.
6. **Windows 10 icons:** navigation uses an operating-system font that is unavailable on the tested Windows 10 installation.
7. **Build diagnostics:** the clean build succeeds but has 82 warnings, including four unawaited-task warnings and multiple nullable-flow warnings.

## Recommended measurement gates for subsequent changes

The next implementation should preserve these baselines and add repeatable checks for:

- time from process creation to dispatcher-ready main window;
- p95 and maximum WPF dispatcher response time while dashboard and fan-control pages are active;
- number and duration of physical hardware-tree updates per minute;
- cache age observed by each consumer;
- process working set, thread count, handle count, allocation rate, and idle CPU;
- behavior with dashboard, overlay, and smart fan control enabled together;
- navigation icon rendering on Windows 10 and Windows 11;
- clean Debug rebuild warning count.

## Limitations

- The reported UI lag was not reproduced as a dispatcher delay on this exact machine during the 30-second probe.
- Runtime behavior varies with firmware, enabled sensor categories, storage devices, GPU drivers, and connected USB/BLE hardware.
- The saved `StartMini=True` setting limited repeatable visible-window timing after the first normal launch.
- No automated test project exists in this revision.
- No application source files were modified during this test pass.
