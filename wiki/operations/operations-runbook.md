# Operations Runbook

## Installation state

The repository does not contain an installer project, packaging script, release workflow, checksums, or a committed release manifest. Runtime code supports two different distribution assumptions:

- The project can publish a self-contained win-x64 file set.
- The in-app updater downloads the first GitHub release asset and then expects `C:\Uniwill.Control.Utility.msi` for `msiexec`.

The source tree alone cannot establish which artifact is the current supported installation method. Any release must preserve all native/content payloads and a stable writable location for the application-directory data and logs. The executable requests administrator elevation.

## First-run prerequisites

| Prerequisite | Detection | Result when absent |
| --- | --- | --- |
| Microsoft VC++ Redistributable | Registry under Visual Studio VC runtime keys | Startup offers the Microsoft download page and exits. |
| PawnIO | Device path and uninstall/version registry data | Deferred prerequisite flow opens the bundled installer UI. |
| RTSS | Process/runtime detection in prerequisite dialog | Optional download guidance; ETW remains the FPS fallback. |
| Compatible hardware | WMI, SKU and device enumeration | Unsupported pages or controls remain unavailable/degraded. |

The PawnIO installer is downloaded from the upstream PawnIO.Setup latest-release URL into a temporary application-data directory, run silently, and then removed.

## Normal startup observations

Expected sequence:

1. Elevation prompt.
2. Short detection delay before the main window is built.
3. Dashboard populated from cached WMI and LibreHardwareMonitor data.
4. Connected-device cards appear as delayed HID/BLE auto-connects complete.
5. Persisted profile, keyboard, light-bar, fan, and battery state is applied.
6. Optional prerequisite/update notifications appear after the dashboard.

Only one UCU process should remain. Launching again should bring the existing window forward through the named event.

## Logging

Logs are written per user, under the local application data directory:

```text
%LOCALAPPDATA%/UCU/logs/ucu_log.txt
```

The file sink rolls daily and limits each file to 8 MiB. Logging level is controlled in Settings through `DiagnosticLogLevel` and the shared Serilog level switch. The sink is never a startup requirement: if the directory cannot be created (a read-only profile, a full disk) logging degrades to the console and the launch continues.

For a useful incident report, capture:

- UCU version and source/release identity.
- Windows edition/build.
- Laptop manufacturer, product and baseboard identifiers.
- CPU/GPU names and firmware/BIOS version.
- Peripheral model, transport and firmware version where applicable.
- PawnIO version.
- Reproduction steps including sleep/resume or navigation state.
- The relevant log file and screenshots.

**The diagnostics bundle does all of this in one click** (About → Diagnostics → *Export diagnostics*, U-208). It writes a zip containing `report.txt` (UCU version, OS, CPU, the engine's `get_info` answer, and the OEM takeover state incl. gate refusals) plus the app log, the engine log, and both takeover journals. The journals are the field-critical part: they are what distinguishes "nothing was paused" from "the restore failed", and three U-203 field rounds had to collect them by hand. Files are read with `FileShare.ReadWrite`, so the currently-open log tails are included; anything unreadable is skipped rather than failing the export.

## Common symptoms

### Application exits immediately after launch

Check the VC++ runtime prompt and registry detection. Confirm all extracted DLLs remain beside the executable. Review the log for host-composition or native-library load errors.

If the saved language is `zh-CN`, the current source catalogue contains invalid JSON at line 389. Catalogue loading occurs before the normal startup logging/exception setup, so this can prevent normal initialization. Reset the saved language to a valid catalogue or correct the JSON in a development build.

### A second launch does nothing visible

The first instance should receive `UniwillControlUtility.Show`. Check whether an existing process is hidden in the notification area. If the process is present but cannot surface, collect its log before terminating it.

### Startup stalls in the "Initializing" phase (60–71 %)

The phase progress reflects deferred tasks, and the game-library scan walks every local volume. A **disconnected mapped network drive** blocks the directory probe in the redirector until it times out (21–63 s measured against a dead host), which is the classic long stall. The scan now skips `DriveType.Network` and the splash releases at a 10 s budget, so the list appears shortly after the window.

Check the app log for "Game library scan outlived the ... startup budget": it names the resource class. `net use` shows mapped drives and their `Disconnected` state. A second machine, or the same drive connected, confirms the environment rather than the app.

### Startup freezes at exactly 92 % "Initializing", forever, reboots do not help

92 % is the top of the Phase-1 tracker: all deferred tasks finished, and the chain is building the main window - the dashboard page constructor. A freeze *at exactly this number, every launch, reboot-proof* is the signature of a **synchronous image decode on the UI thread** being held by a security product's file filter: WPF's `BitmapImage` decoder resolves the picture's ICC color context through a synchronous `FileWebRequest` on `C:\Windows\System32\spool\drivers\color`, and a guard that system directory (observed: Emsisoft) parks the open's IRP indefinitely - the dispatcher thread never returns, so the window paints its last progress value and freezes. `dotnet-stack report -p <pid>` shows it directly: the UI thread sits in `FileWebRequest.GetResponse` under `BitmapImage.FinalizeCreation` under the page constructor. The app is not corrupt and the install is not broken; the AV's system-directory guard is the machine condition, and an AV allowlist for the app (or the guard off for its file opens) is the permanent fix on that machine. The product-side fix is the rule the code now follows: images decode off the UI thread with a bounded wait (`SafeImageSource`: pool-thread decode, `IgnoreColorProfile` to skip the ICC file open, cache-on-load + freeze, 5 s budget, image collapses on failure) - the worst case on a guarded machine is a missing laptop photo, never a frozen pre-loader.

### The window appears, metrics stay missing, then the whole app freezes with the dashboard up

The second member of the guarded-machine freeze family; the window paints, so it reads as "it loaded, then froze" rather than a splash stall. `dotnet-stack report -p <pid>`: the **UI thread** sits in `Monitor.Enter` on `HardwareMonitoringService.Acquire` (reached from a device-connect dispatcher callback via the lazy temperature lease), and the lock holder is a refresh thread parked in a storage `DeviceIoControl` (`DiskInfoToolkit...OpenDevice`) inside LibreHardwareMonitor's update pass - a filter driver holding the disk open indefinitely. Root cause was one lock guarding both lease bookkeeping and the entire hardware update, so any hung driver probe froze every UI consumer of the metrics service. The product-side rule the code now follows: **no app thread performs hardware I/O or waits behind it** - lease bookkeeping is a dictionary-only lock, all driver I/O is serialized on a probe gate that only pool threads block on, a hung probe parks a single pool pass, and the dashboard is served an OS-only snapshot (kernel32 battery + `GlobalMemoryStatusEx` + EC CPU temperature, merged with the last completed LHM values) while the probe is stuck. On a guarded machine the dashboard therefore fills battery/memory/EC-CPU numbers with the probe hung; LHM-only fields stay `--`. Verification launches must use the product's real route - **unelevated**: an elevated token passes AV service protection and the PawnIO device ACL, so elevated test runs hide exactly the defects guarded machines surface (blank metrics, service-descriptor denials) and are not proof.

### PawnIO-backed controls are unavailable

Open the prerequisite flow and verify PawnIO is installed and its device path exists. Confirm the correct AMD or Intel module files were copied into the application output. Restart UCU after driver installation.

When the driver is installed but its device is absent, suspect a **Core Isolation (Memory Integrity) block**: the engine log line `AMD PawnIO failed to initialise. (Win32 1275 opening ...)` names it (1275 = the driver was blocked by Core Isolation policy — the same code OpenRevo's driver manager recognizes from `StartService` in `bld_driver_mgr.rs`; 577 = the image failed integrity-hash verification). On an install failure the app shows the named copy "Memory Integrity is blocking the driver" with the Windows Security button. **1275 does not mean Memory Integrity must be turned off**: the latest PawnIO release is signed to load with it enabled and the in-app installer always downloads that latest release — re-running the installer and restarting UCU is the remedy. If the block persists, the machine's Code Integrity policy blocks this driver and the PawnIO-backed controls stay unavailable; disabling Windows security features is not a supported remedy.

### The engine service is not created at all

The app registers the service in its post-startup chain, so a service that never appears means that chain never ran: read the app log (`%LOCALAPPDATA%\UCU\logs`) for the phase markers and the `[Engine]` lines, and the engine installer's own log (`%LOCALAPPDATA%\UCU\engine\install<yyyyMMdd>.log`), which records every `sc` step with its exit code. An install log with no entry for the launch means the app never reached the ensure - a frozen window is the usual cause, because the chain runs after the window renders. `sc create` failing with 1073 means a registration exists (a leftover), and 1072 means it is delete-pending: on a machine whose policy relaunches stopped services, an uninstall verb's `sc stop` can leave the registration delete-pending while the policy runs the image again; the verb's force ladder (kill the service process, retry the delete) resolves it, and a tombstone from an open `services.msc` blocks re-creation until the last handle closes.

### Dashboard CPU temperature shows `--`

The CPU's own sensor requires the PawnIO driver, and PawnIO's device ACL admits System and Administrators only - an installed, unelevated app cannot open it even when the driver is installed and running, which is the normal state of a per-machine install. UCU then displays the embedded controller's reading and the card's tooltip names the source ("Embedded controller sensor"), so a value from the EC is expected, not a defect: the two sensors are not the same number.

`--` means neither source answered. Check that the engine is running (`sc.exe query UCUEngine`) and that its log (`%ProgramData%\UCU\engine\`) reports the EC driver opened; an engine-side loss shows `--` on every EC-fed card (fan speed, battery health) at the same time. A tooltip reading "CPU core sensor" with no value points at the PawnIO path (driver installed, device openable, module files present).

### Dashboard CPU Power / Clock Speed / RAM Speed cards show `--` (per-machine install)

Field report 2026-10-29 (guarded box, the user's double-click route): at launch CPU Power, CPU Clock Speed and RAM speed never appeared; GPU power/clock appeared ~30 s later. The causes are the ACL rule above generalized: CPU package power and core clocks are **Ring0 MSR** readings and the DIMM SPD data rate is an **SMBus** reading - the sensor drivers' device ACLs admit System + Administrators (PawnIO's INF ships `D:P(A;;GA;;;SY)(A;;GA;;;BA)`), so the asInvoker app installed per-machine gets access denied and these cards stay `--` for the whole session. The GPU cards fill late because NVAPI needs no driver - the app's own LHM probe is what parks at startup under resident AV, and it opens at ~+30 s.

The remedy is the **engine-side sensor snapshot** (`telemetry.get_metrics_snapshot`, the one documented exception to the EC-only verb surface - the standing rule keeps SMU/PawnIO/Intel/NVAPI app-side; the field evidence that unelevated reading is structurally impossible justifies exactly this one cached read, and the GPU stays app-side): the LocalSystem engine runs a CPU+Memory LHM probe on a dedicated loop (MetricsProbeService), publishes to a cache, and the verb answers from the cache (inline, never behind the EC queues; a parked probe parks only its own loop). The verb stamps the cache's serve-time age into the answer (`ReadingAgeSeconds`), and the app gate (`EcTelemetryService.ReadEngineMetrics`) turns a stale answer into Empty - the `--` value: the probe loop deliberately runs OUTSIDE the engine watchdog (a wedged sensor open must not FailFast an engine whose EC queues are healthy), and the app's stale-while-revalidate cache keeps serving the last DTO forever when the engine dies, so without the stamp both failure faces paint frozen numbers as live (field audit 2026-10-29). Budget: 30 s, ~6 probe cycles - **a card flipping to `--` ~30 s after the engine dies or its probe loop wedges is correct behavior**; the defect was the 104 W statue, not the `--`.

The engine values merge at the **snapshot producer** (`HardwareMonitoringService.ApplyEngineSensorSource`, beside the EC-temperature merge, applied on every served snapshot in `ApplyOsSources`), filling only the fields the app's own probe left 0 (a live in-process reading always wins; zero is the snapshot's "unavailable" convention), so EVERY consumer - dashboard cards, tray flyout, FanControl cards, the RTSS OSD - gets the engine-fed fields through the same `ReadSnapshot()` (the first fix merged at the dashboard timer and starved all the rest; field report: the OSD showed none of what the dashboard cards showed, 2026-10-29). The GPU fields are untouched (NVAPI stays app-side; there is no engine GPU reading to overlay). The SPD speed paints the RAM card's system-info cache when the WMI source is 0/late (`CachedSystemInfo.PublishRamSpeedIfMissing`, an idempotent 0-to-value transition firing the card's repaint exactly once). The tray renders 0 power/clock as `--`, never the fake `0 W`/`0.0 GHz`.

Diagnosis: the engine log's `sensor probe not open; retrying in 00:01:00` lines show the sensor stack failing (no sensor driver, asInvoker engine - the dev F5 case); a healthy engine shows nothing (the probe logs only failures/slow cycles). The app-side path: engine running + cards still `--` → the probe is open with silent sensors (driver installed on demand by LHM at SYSTEM; a security product blocking the RAMSPD driver load leaves SPD fields 0 - WMI stays the RAM-speed source, and a platform reporting `ConfiguredClockSpeed = 0` shows `Not available` honestly). Cards fill, then flip to `--` ~30 s later → the freshness gate is rejecting: the engine died (check `sc.exe query UCUEngine`), its verb is answering too-old stamps (`verbprobe` prints `age=`), or the probe loop wedged (the loop is outside the watchdog by design, so a wedged open keeps the engine alive and ages the cache - the flip to `--` is the mechanism working). The engine's probe sensor naming is pinned by unit tests to the field machine's empirical elevated probe (power `Package`, clock `Cores (Average)`, SPD `tCKAVGmin` -> 5602 MT/s = the machine's WMI 5600); a library update that renames sensors fails those tests, not the field.

**In-game: metrics freeze, updating 1-2 s around every alt-tab** (field report 2026-10-29, the RTSS OSD): the signature is values frozen mid-game that update briefly each time focus switches - the app-side **LHM probe pass** parks behind the foreground title that owns the GPU (NVAPI/storage calls under AV filter drivers; exclusive fullscreen is the classic parker), and the snapshot cache is single-flight: a parked pass queues no new pass, so the last completed snapshot is served as live indefinitely. The producer's freshness rule closes the statue: past the 5 s probe-staleness budget every LHM-only field is rendered `--` (GPU row, CPU usage; nothing to paint that the producer alone feeds), while the fresh sources keep answering live through the OS-only path - OS memory/battery, EC CPU temperature, **engine-fed CPU power/clock and DIMM temps keep updating in-game** (that is what the engine feature is for). Confirm the park site: `dotnet-stack report -p <app pid>` while frozen shows a thread parked in `_probeGate`/`Computer.Update` (NVAPI or a storage `DeviceIoControl` frame names the driver); the user-side remedy is borderless-window game mode, which usually unblocks the pass.

**The first launch after installing a new build is slow (minutes), later launches are seconds** (measured 2026-10-29: first-launch `Computer.Open` 64844 ms vs 1458 ms steady state, per-subsystem matrix all sub-2 s under the same unelevated token): a security product scrutinizes every fresh binary hash on first use, and the LHM open is where the app touches drivers. The producer keeps serving OS/EC/engine fields throughout (first-frame gate + staleness rule), so the dashboard is usable while the LHM-fed fields fill. Not an app defect; the per-machine remedy is an AV allowlist for the install root, the product remedy is code signing.

**A SMART park serializes the whole producer - Storage is gated to a 60 s cadence** (field breadcrumb 2026-10-29: `device update Storage "CT2000P310SSD8" 21044ms`): the SMART DeviceIoControl behind an AV storage filter sat inside the probe gate, which serializes every device's update, so the fast sources (GPU, CPU) aged past the staleness budget and the LHM-fed fields blanked everywhere. Storage temperature is quasi-static; the probe loop now updates Storage once a minute (first update deferred a minute so the first snapshot never queues behind SMART). The slow-device breadcrumb stays: it named this, and it names the next one.

**The producer is two probe groups, so one park costs two cells instead of the dashboard** (2026-10-29): the single `Computer` gave every subsystem ONE gate and therefore ONE age - the 21 s SMART park above aged the WHOLE producer, and the freshness rule then correctly blanked every LHM-fed field on dashboard, tray, FanControl and OSD while a quasi-static disk temperature was being read. `HardwareMonitoringService` now runs a **fast group** (`cpu`/`gpu`/`battery` - the CPU-utilization and GPU-row fields; open cost measured 97 ms + 1123 ms + 33 ms) and a **slow group** (DIMM SPD, SMART, motherboard/controller SuperIO, carrying the SMART cadence gate), each with its own gate, cadence, staleness age and breadcrumb prefix (`[LHM] probe: [fast] ...`, `[LHM] probe: [slow] ...`). The merge (`MergeGroupSnapshots`) clears a stale group's own fields and nothing else, and the OS/EC/engine sources refill their fields beside it. `ReadSensor` routes by hardware type (motherboard/controller fans → slow, CPU/GPU fans → fast) and gates on the routed group's age, so a parked SMART read stops feeding 0 RPM to the adaptive fan loop. Group rebuilds are driven by each group's own mask because LHM's kernel side (WinRing0/PawnIO) is process-global: closing one group releases the shared handle the other is using.

**The main window blips for one frame at 92 % of the pre-loader - fixed by parking BEFORE the first Show** (field report 2026-10-30): the gated `MainWindow.ShowWindow()` did `Opacity = 0` → `Show()` at the CenterScreen position → park off-screen, and this window's backdrop (`WindowBackdropType="Mica"`) is composited by **DWM**, which WPF's `Opacity=0` does not hide - so a 1080x1080 rounded panel painted one frame at screen center while the splash, a 320x290 card, exposed the whole screen around it (92 % is exactly where the `ParallelPhaseTracker`'s 50→92 span ends and the host starts). Three order rules close it: park before the first `Show()` (`WindowStartupLocation.Manual` + off-screen offsets, so the window's very first composition is off every monitor edge - `Show()` is still required, NavigationView's template only applies through a real Show, field-proven NREs otherwise); `Loaded`'s `FitWindowToWorkArea` skips the parked window (`Screen.FromHandle` on a parked window resolves the **nearest** monitor and the re-center drags it back on-screen); App plays out and **closes the splash before** `ReleaseStartupGate` lands the window at the work-area center, then raises opacity - the window's first visible presentation is the populated dashboard, nothing paints beside the splash. Measure a presentation artifact like this objectively instead of eyeballing it: enumerate the app's top-level windows (`user32 EnumWindows` + `GetWindowRect`) every ~20 ms across the pre-loader. Healthy shape (measured 2026-10-30): the card alone on-screen, then the main window visible **only at x=-32000 while the card is up**, then the main window on-screen after the card is gone. Blip signature: the main window visible with an on-screen rect while the card is up.

**A UAC consent prompt the app did not ask for - a reflected toggle actuated a device** (field reports 2026-10-30, three rounds). The Settings page writes state into its toggles in three places - the constructor's saved-settings init, the load-time `SyncHardwareManagementStates`, and the Wi-Fi/Bluetooth `StateChanged` listeners - and its `Checked`/`Unchecked` handlers **actuate**: the webcam row's `SetWebcamAsync` runs `powershell.exe` with `Verb=runas` (the reported prompt), the touchpad row runs `SystemSettingsAdminFlows.exe` elevated, a saved "start on boot" reflection re-registers - or **unregisters** - the scheduled task, and the CPU Advanced Performance Menu reflection writes NVRAM. Opening the page, and in the last round **starting the app**, performed mutations the user never asked for.

Two mechanisms made this hard, and both are field-proven:
1. **WPF-UI's `ToggleSwitch` raises `Checked`/`Unchecked` in a LATER dispatcher pass**, not synchronously from the `IsChecked` write, so a guard flag set around the write was already released when the handler ran (the first fix leaked exactly this).
2. **The toggle's own XAML `IsChecked="True"` is applied in its TEMPLATE pass** and raises from there - after the constructor has run. With the belief of the four device rows still `null`, a state comparison read `true != null` as user intent, and at startup all four rows actuated (app log, Information severity: `[Settings] webcam actuating: toggle=true belief=null`, then `[Elevation] Webcam PnP toggle ...`, `[Elevation] Touchpad admin flow ...`).

The rule that closes the class: the page keeps what it **believes** each actuating row is in, and a `Checked`/`Unchecked` event is user intent only when the toggle's state differs from a **known** belief (`belief.HasValue && toggle.IsChecked != belief`). Every reflected write (init, sync, radio event) moves the belief together with the toggle, so the event - whenever it arrives - sees equality; an unknown belief is never intent, because the page cannot have been asked to change a state it never observed. The rule lives in one helper, which logs both directions: `[Settings] {row} actuating: toggle=... belief=...` (Information) and `[Settings] {row} reflection, not intent: ...` (Debug). Diagnosing this class is then a log read at Information severity, no reproduction needed; set it with the Settings page's log-level combo (index 2 = Information, 3 = Debug, `DiagnosticLogger.ApplySettingsLevel`).

Measure the effect objectively rather than by asking whether a prompt appeared: launch the app unelevated (`runas /trustlevel:0x20000`) and watch the process tree - the defect's witness is a `powershell.exe` child of the app PID carrying `-WindowStyle Hidden` (that flag only exists on the elevated `ElevatedProcess` form) or a `SystemSettingsAdminFlows.exe` child; the pass is the same events logged as `reflection, not intent` with zero elevated children. Driving the page by UIA is possible: the nav item is a `DataItem`/`ItemsControlItem` exposing no UIA pattern, so it is clicked at its `BoundingRectangle` centre, and the click must wait for the startup gate (the parked window sits at x=-32000, and clicking a parked window is a no-op).

**The per-operation consent prompt on the device rows - relocated to the engine** (2026-10-30). The webcam and dGPU PnP mutations were the unelevated app's remaining `Verb=runas` sites, and the dGPU one is reached from **five automatic paths** - GPU power saving applies at startup, on charger transitions, on resume, from the tray quick-control, and from Automations - so the prompt was structurally unreachable: an automatic apply can never require consent. They are now engine verbs (`device.get/set_webcam_enabled`, `device.get/set_dgpu_status/enabled`): the LocalSystem engine performs the **CM API** mutation directly (`CM_Enable_DevNode`/`CM_Disable_DevNode` - what `Enable-PnpDevice` calls internally; no `powershell.exe` child for an AV to flag, no consent), and the verb answers only after the engine's own verification re-read of the devnode. The elevated PowerShell routes stay as the **fallback for a machine whose engine is not answering**, behind a breadcrumb naming the reason. The trust boundary did not move: the pipe DACL (`PipeSecurityBuilder`) already grants the console user `mux.set_mode` and power-limit writes, so camera/display PnP is below the existing reviewed boundary. The touchpad's `SystemSettingsAdminFlows.exe EnableTouchpad` needs a full administrator token **in the interactive session**, so it cannot run in the engine's session 0; it runs as a one-shot scheduled task registered by the app's owner at `TaskRunLevel.Highest` with a passwordless S4U logon - the route the Windows Settings app itself uses for that flow - on-demand only (no persistent trigger), deleted after the run, 15 s poll; the direct elevated spawn stays as its fallback. The honest signals that rode along: `GpuPowerSaving.ApplyAsync` logs `PnP verified: {True/False} (status: ...)` with the re-read status instead of an unqualified "applied successfully" (it logged success even after a **declined** prompt), and `NvTuning.SetClocks` no longer returns success on a write the driver refuses - GeForce reports the performance-states capability read-only, and that refusal is now visible in the log. Diagnostic fingerprints after the relocation: toggling the webcam by hand spawns **no** process child (the CM call is in the engine; the row's status re-query is the only plain `powershell.exe` child), toggling the touchpad shows a transient `UCU Touchpad Flow` task (`schtasks /query /tn "UCU Touchpad Flow"` during the act) and no consent dialog; before it, both were a `powershell.exe -WindowStyle Hidden` child.

**The engine's PnP enumeration died on the field box — identity moved to WMI** (2026-10-30, p52 field report). The Webcam toggle answered `verified=false` without touching the devnode, and the engine log said why: `CM_Get_Device_ID_List failed: 0x00000004` then `Camera already disabled, no mutation (present-matching found: false)`. Diagnosis by raw P/Invoke matrix on that machine: **every** `CM_Get_Device_ID_List` call shape (W and A, every filter, every documented PMCL flag set) answers `CR_FAIL`/`CR_NO_MORE_HANDLES`, and the FriendlyName/Class devprops answer `CR_NO_SUCH_VALUE` on nodes whose `CM_Get_DevNode_Status`/`CM_Locate_DevNode`/mutation calls work — the CM **enumerator and property reads** are machine-broken while the **per-node** calls are healthy. The box also registers its cameras under a non-standard class GUID (`{ca3e7ab9-…}`, the registry's "Camera" class), and the friendly names the rows match ("FHD WebCam", "IR Camera") exist nowhere in SetupAPI/registry properties — they are `Win32_PnPEntity.Name`, the WMI composition `Get-PnpDevice -FriendlyName` rides (the app's own elevated fallback). The engine service therefore identifies devices through WMI (`SELECT Name, DeviceID FROM Win32_PnPEntity WHERE PNPClass='Camera'` + the wildcard match) and keeps the CM per-node calls for status, mutation, and the verify-by-re-read. The honest-answer chain earned its keep: the verb's `verified=false` flipped the toggle back and named the reason in two log lines, which is what made the field report precise. A WMI enumeration failure logs as `[PnpDevice] WMI enumeration of class … failed: …` — an empty machine visible, never a silent no-op.

**…and the legacy DF status bits are dead on modern Windows — status comes from the problem code** (same box, same day, the fix's second half). With identity on WMI the rows still read NULL: `CM_Get_DevNode_Status`'s legacy `DF_PRESENT`/`DF_RUNNING`/`DF_DNE_0` bits answer `0x0180600A` on HEALTHY running nodes — no present, no running, DNE set — on the webcam and the dGPU alike. Ground truth via Disable/Enable-PnpDevice on the FHD WebCam: disabled → `pulProblemNumber=CM_PROB_DISABLED(22)`, WMI Status=Error, Present=True; enabled → `prob=0`, Status=OK. The problem code is the live signal; `Describe` maps 0="OK"/running, 22="Disable", 45=`CM_PROB_PHANTOM`→not present/"Unknown", other="Error". Any new code that reads devnode state must use the problem code, never the DF bits.

**…and `DICS_DISABLE_GLOBAL_W` is rejected — the disable call shape is `(0, DICS_FLAG_GLOBAL)`** (same box, p55 field report 19:00, `beaa1b0`). With identity and status fixed, the user's session showed the engine finding both camera nodes, selecting targets — and `CM_Disable_DevNode` answering `CR_FAIL (0x4)` on both (`disable USB\VID_2B7E… returned 0x00000004` → `verified=false`). Call-shape matrix on the live webcam node: `(DICS_DISABLE_GLOBAL_W, 0)` → 0x4, `(DICS_DISABLE_GLOBAL_W, GLOBAL)` → 0x4, `(0, DICS_FLAG_GLOBAL)` → **0x0 with prob=22** (CM_PROB_DISABLED — the state Disable-PnpDevice's ground-truth run leaves), `CM_Enable_DevNode(inst, 0)` → 0x0 restoring prob=0. The flag is rejected by this Windows from every caller (the admin shell included) — it is not an engine-context problem; the engine's LocalSystem identity was never the suspect, the honest `verified=false` chain again named the exact call. The layering is the lesson: one field report, three dead layers peeled by the breadcrumbs each fix exposed — enumerator→identity, DF bits→status, flag→mutation. The app-side pin asserts the exact `CM_Disable_DevNode(device.DevInst, 0, Native.DICS_FLAG_GLOBAL)` call text.

**The silent-death rows - NVRAM, SMU, Intel MSRs, MiniLED WMI - relocated to the engine** (2026-10-30, the elevation audit's second sweep). These four families never prompted: the privileged APIs **deny an asInvoker token outright**, so the rows were silently dead on the guarded field machines - the toggle saved, the register never moved, no prompt to explain. Field shape per family, and where each actuates now:
- **NVRAM** (`SeSystemEnvironmentPrivilege`, unwritable unelevated): the CPU Advanced Performance Menu row's support probe found nothing (row hidden), its write failed with access denied, and the GPU mux's firmware mirror (`OemMagicVariable` offset 98) never persisted. Engine verbs `device.get/set_nvram_value`, `device.get_supports_cpu_ap_menu`, `device.set_cpu_ap_menu_unlock` (the offsets-111/51 pair is ONE verb, read-patch-write verified by re-read, so the pair cannot half-update). The app seam is `NvramAccess`; the pages' direct `Get/SetFirmwareEnvironmentVariable` P/Invokes survive there as the fallback, and Display's NVRAM probe is no longer gated on `_isAdministrator`. Every write of the OEM entry — engine verb, AP-menu pair-write, app-side fallback — first unlocks the 50-series gatekeeper variable `OemMagicDoor` (one byte, 0x01; the reference's handshake, open-revo `uefi_nvram.rs`): the engine log lines are `[FwNvram] OemMagicDoor unlocked … (attempt N)` then the entry's `write … ok` + `readback verification: True/False` evidence line; `OemMagicDoor unlock failed - refusing the OemMagicVariable write` means the entry was NOT touched; `OemMagicDoor absent - no gatekeeper on this firmware` is a firmware without the door variable (the entry is written directly, the door is never created).
- **AMD SMU** (PawnIO device ACL = System+Administrators): Curve Optimizer and every SMU preset apply was dead (the app's driver open is access denied; the apply throws into the batch's log). Engine verb `cpu.execute_amd_smu_command` on the new **cpu queue**; `UCU.Hardware\Cpu` carries the app's SMU stack **verbatim-ported** (native register code re-homed, not rewritten; the duplication with the app's copy is the architecture - the app can never load the hardware assembly). `SmuAccess.Execute` reports the SMU's own status code (`[Smu] {command} ... via engine: status=0x{...}`); HardwareUnavailable/Timeout/Busy fall back locally, a HardwareFault rethrows (never papered over by the access-denied local open).
- **Intel MSRs** (same PawnIO device): TDP 0x610, voltage 0x150 (cpu/gpu/cache/sa planes), ratio 0x1AD, power balance 0x63A/0x642 - every Intel preset apply was the same silent death, swallowed by the app methods' catch-and-log. Engine verbs `cpu.intel_set_tdp/_set_power_balance/_set_voltage_offset/_set_clock_ratio/_get_clock_ratios`, per-register-set (a raw write-MSR-by-address verb would widen the boundary; these are the same power authority the EC power verbs grant). `IntelManagement` routes engine-first and logs `landed=True/False`. The HKLM **driver-blocklist write** (`CI\Config VulnerableDriverBlocklistEnable`) is retired, NOT relocated - a LocalSystem service must not weaken the vulnerable-driver blocklist.
- **MiniLED local dimming** (executing the OEM `AcpiTest_MULong.GetSetULong` root\WMI method needs namespace write access): the Display row and the tray row were dead. Engine verb `device.set_mini_led_dimming` runs the enable pair `0x50000000002/0x5000000000E` (expect reply bytes `0xBB/0x0E`) and the disable pair `0x...1/0x...D` (expect `0xAA/0x0D`) as LocalSystem; the firmware's reply byte is the witness, and the EC `0x72B` bit-`0x02` readback verify stays app-side on the telemetry verb. The WMI dependency now lives engine-side (`System.Management` is on the UCU.Hardware allowlist with this justification; the QKey **event read** stays app-side - reads are standard-user acts).

Routing rule shared by all four (the **fallback-first** shape): the engine verb is the FIRST route; the app's original privileged code survives as the fallback for a machine whose engine is not answering, reached only on the `HardwareUnavailable/Timeout/Busy` codes, and every switch logs the reason (`... via engine: ...` / `engine not answering ({Code}) - using the local route`). Diagnosing a field row is then a log read: the breadcrumb names the route that answered, and the engine log (`%ProgramData%\UCU\engine\`) names the win32/HRESULT/status reason. Dead-code companions retired in the same pass: `Run_CLI` (its `Verb=runas` under `UseShellExecute=false` is inert - game launches are plain shell-execute now) and the `Verb="runas"` on the Display restart button (the console user holds SeShutdownPrivilege; the verb only bought a prompt). The overlay-scheme applies are NOT a privilege site (standard-user powrprof act) - their fix is the witness: the return status is now logged (`Win power overlay -> {scheme}: status=0x{...}`).

**The in-app LHM open costs far more than the subsystems do** (measured 2026-10-29, guarded box, unelevated token): the identical Computer config in a standalone process opens in **1.458 s** (per-subsystem matrix, fresh process each: cpu 97 ms, mem 69 ms, gpu 1123 ms, battery 33 ms, motherboard 97 ms, storage 211 ms, controller 85 ms), while the app's own breadcrumb logged **64619 ms** on a fresh pack's first launch, **22256 ms** on the next, and **no slow-open line at all** on a third. The variance tracks the security product scrutinizing the app process (fresh binary hashes on first use, easing as reputation builds), not the subsystems. The split bounds what such a stall can hide (only the fields of the group being opened), and the ordered kick - fast group opens first, the slow group starts when the fast pass settles - gives the watched fields the driver race. Stack sampling the app during startup (`dotnet-stack report -p <pid>` every 3 s) caught a probe thread parked at `NvidiaGpu.Update() → NvmlDeviceGetPcieThroughput`: NVML calls park under load as well, and per-group freshness is what turns that into `--` for the GPU cells only.

### The engine service is installed, stopped, and the app does not start it

The app owns the engine's lifecycle and starts a stopped engine unelevated, because the service DACL grants Authenticated Users `SERVICE_START` (RP). When the app logs `Could not start the engine service` / `not allowed to start it` with native code 5 (`Access is denied`), the registration carries a DACL from a build that predates the grant - typical after an `msiexec /x` uninstall, which leaves the registration (and its DACL) behind, followed by a reinstall.

`sc.exe sdshow UCUEngine` must read `D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;CCSWRPRC;;;AU)`. The service re-asserts this itself (`ServiceSelfSecurityService`: on start and every 5 minutes, `SetServiceObjectSecurity` from LocalSystem) - and that is load-bearing, not belt-and-braces: security products with service protection (observed: **Emsisoft Anti-Malware**) revert `sc sdset` immediately (SUCCESS then template on read-back, every ordering, and the SACL `S:(AU;FA;...;;;WD)` is the enforcer's fingerprint). Diagnose with `sc sdshow` plus, under the template, an unelevated `sc query UCUEngine` answering 5 while the app is running. The app repairs an unrecoverable descriptor with one elevated install (`sc sdset` + start, logged in `%LOCALAPPDATA%\UCU\engine\install<yyyyMMdd>.log`); the classic symptom of a reverted descriptor is a UAC prompt for "Uniwill Control Utility Engine" on **every** launch with the install log showing `sc start ... FAILED 1056` against an already-running service. If the window freezes (painted, splash overlay stuck), capture a dump first - Task Manager → right-click the process → Create dump file - `dotnet-dump analyze <dmp> -c clrstack` names the frozen frame (a real case: the UI thread inside `SetWindowsHookEx` from the overlay hotkey hook). Supervision signatures in the engine log: `App stopped ... graceful=false → Relaunch` followed by `[Supervision] Launched the app in session N` is the crash-respawn working; `EntryPointNotFoundException: WTSGetActiveConsoleSessionId` was a real defect (the import named `wtsapi32.dll`, the export lives in `kernel32.dll`) and its stack ending in `BackgroundService failed ... StopHost` shows why a supervision throw must be caught per tick - unhandled, it took the whole engine down (RPC and watchdog included), and the SCM failure action (restart/60000) was what brought the engine back.

### Raw-write gate refusals (engine log: `[Gate] raw write ... outside the allowlist`)

The raw EC verbs (`fan.write_register_blocks`, `telemetry.write_register`, `device.set_nvram_value`) carry caller-chosen addresses/GUIDs; the server-side gate (`EcRawWriteGuard` + `UCU.Core\Ec\EcWriteGatePolicy`) refuses targets outside the fan-table/PWM/keyboard/battery-mode domains and foreign NVRAM GUIDs. In the engine log a refusal is the dispatcher's BadRequest line naming the target (`raw write to register 0x0783 is outside the engine's allowlist`); the client sees `EngineException` with code `BadRequest` and **the EC is untouched** (the gate runs over the whole parameter set before the first write, so a mixed plan applies nothing). Semantic-verb value refusals are the codec validators: the client sees `InvalidValue` (`duty percent must be 0-100, got 150`), logged at the dispatcher. Production callers use only allowed domains — the smart-fan planner (fan tables) and the NVRAM rows (the `OemMagicVariable` GUID) — so a gate refusal in the field means a caller regressed onto a raw verb or the allowlist is too strict for a chassis. The field-debug escape valve: run the engine interactively as `"...Uniwill Control Utility Engine.exe" --console --gate=report-only` (dev box, after `sc stop UCUEngine`) — refusals then log as `[Gate] raw write ... — allowing (gate=report-only)` and pass through, which identifies a too-strict allowlist without reflashing. The codec value checks are never report-only: a bad value stays refused in every mode. Never set the flag for the installed service.

### The uninstall left pieces behind (forensics)

The complete uninstall is an app-side self-heal: Control Panel / Settings runs `msiexec /x`, the MSI removes its thin registration, and the running app's `UninstallSentinel` notices the registration gone within ~10 s and self-runs the engine's `--uninstall-engine` verb as SYSTEM (one-shot `/ru SYSTEM` scheduled task `UCU Uninstall Verb`), which performs the full sweep (service, app processes, tasks, ARP husks, per-user hive husks, stale per-user MSI registrations, logs, layout). Firing requires **removal evidence**, not just a missing registration: the Application event log must show, within 3 minutes, MsiInstaller 11724 "Removal completed successfully" naming the product AND 1042 "Ending a Windows Installer transaction: {code}" for the product code the sentinel watched while the registration was visible - and, for the destructive firing, **both events must postdate this app process's start** (the time floor, unit-pinned in `StaleRemovalEvidenceTests`): pack.ps1 pins the product code per package, so an uninstall-reinstall of the same package within 3 minutes reuses the code, and the user's previous uninstall fingerprint would otherwise license the verb against the fresh install (field-proven 21:55:22: shim uninstall at 21:53:59, reinstall at 21:55:06, the relaunched sentinel executed the stale fingerprint and swept the fresh install 16 s after launch). The evidence rule is field-proven necessity: an AV with ARP-key protection (observed: Emsisoft) makes the live registration invisible in the app's own registry view - a phantom miss on every poll, while msiserver and SYSTEM see it fine; without evidence the sentinel would self-delete a fresh install ~16 s after every launch (and the 3-minute window + code binding + process-start floor stop *older* uninstalls from licensing a fresh install). The sentinel logs the parked phantom at Warning severity. Diagnose a dirty machine by reading the two traces: the app log (`%LOCALAPPDATA%\UCU\logs\ucu_log<yyyyMMdd>.txt`) for `[UninstallSentinel]` lines (parked phantom / fired / "verb task created (SYSTEM) rc=" / "FAILED to fire the verb"), and the verb's install log - elevated launches log to `%LOCALAPPDATA%\UCU\engine\install<yyyyMMdd>.log`, the SYSTEM task logs to `C:\Windows\System32\config\systemprofile\AppData\Local\UCU\engine\install<yyyyMMdd>.log`. The most common sentinel failures, all field-proven:

- **The sentinel never armed** - the layout signal root must be exactly one level above the app image (the app runs at `<root>\current\`); a root that resolves to a generic directory (e.g. `C:\Program Files`) never carries the marker, so the watcher idles forever. Arming requires an install layout under Program Files with `Update.exe` plus an existing `HKLM\SYSTEM\CurrentControlSet\Services\UCUEngine` key.
- **The sentinel never started** - it must be launched right after logging init, before the blocking startup stages. On machines where startup blocks (the modal PawnIO prerequisite dialog, slow EC init), anything wired into the post-startup chain starts too late - after Control Panel's "no dialogs" uninstall window has closed.
- **The verb task dies at `schtasks /create`** - 0x5 (Access Denied) from the UAC consent with `RUNLEVEL LIMITED` (a medium-IL un-elevated process cannot register a SYSTEM task: the verb task must be created by an elevated context - in practice by the app when it is running elevated, which the install flow already does). 1008 / "The syntax of the date, time is invalid" means Task Scheduler mangled the `/tr` string: it cannot carry escaped quotes (`\"`), so the task action is `cmd.exe /c <script>` with all quoting inside the script files, and the script path must be an 8.3 short path (`GetShortPathNameW`) - a long path containing spaces splits in cmd's parser.
- **The verb ran but `sc delete` parked** - the machine's policy relaunches stopped services, so the delete sits pending; the verb's force ladder kills the service process and retries (the verb process shares the engine image, so the ladder must exclude its own pid).
- **The layout root survives** - a security product's file-guard self-defense (observed: Emsisoft) can deny layout-root deletion to SYSTEM and Administrators alike. On such machines the verb logs the access-denied and the root survives as an inert husk; everything user-visible (service, ARP, tasks, app) is gone. The fix is an AV allowlist for the install root, not a product change.
- **A "Uniwill Control Utility" husk remains in Control Panel after the product is gone** - stale per-user MSI registrations (`HKCU\...\Installer\Products`, left by machine-WiX per-user ghost products, Velopack, and interrupted runs). `MsiEnumProductsW` sees them while the ARP key is gone; the husks are unremovable through Control Panel because the MSI's cached package no longer exists (`1619 "This wizard cannot access the setup database"`). The verb sweeps them (`/x` first, registration-key surgery when `/x` fails); Control Panel refreshes its listing lazily, so re-open it before concluding.
- **The app is in Task Manager with no window, and elevation prompts repeat during an uninstall** - engine supervision relaunches the app while the verb sweeps it. `UninstallSentinel.IsBeingUninstalled()` gates relaunches/starts during the sweep window (ARP registration gone + layout present).

Manual reproduction: run the verb directly with the systemprofile logging visible - `schtasks /create /tn "UCU Uninstall Verb" /tr "cmd.exe /c <short-path script>" /sc ONCE /sd <near-future> /st <time> /ru SYSTEM /rl HIGHEST /f` then `schtasks /run`; the script content is `"<engine exe>" --uninstall-engine >> "<log>" 2>&1`. The MSI's own surface is only the registration and ARP entry - the layout is deployed by the packer's bootstrap custom action, which is why `msiexec /x` alone removes almost no files and why the self-heal, not the MSI, owns uninstall completeness.

### The app self-uninstalls a minute after the dashboard appears (Velopack registration repair)

Signature: fresh GUI install → app launches → dashboard fills → ~15-60 s later the app dies; the Application event log shows the app's own process running `msiexec /x {the live product code}` (MsiInstaller 1040/11724/1042, Client Process Id = the app), and the verb log shows the sentinel's sweep executing that genuine, code-bound removal. The sentinel is innocent: this removal is real, watched, and bound - the app killed itself.

The mechanism: Velopack's per-machine registration check is an IN-PROCESS registry read (MSI classes/Installer hives + ARP). A security product that polices registry keys (observed: Emsisoft) blinds those reads for app processes, inconsistently per hive - field-proven from BOTH directions on one machine: ARP-blind while MSI-classes visible, and ARP-visible while the MSI-classes read blind. In either blinded state Velopack concludes "the install is not registered" and its repair runs `msiexec /x` on the LIVE product code ("re-register"), which arms the sentinel's full sweep.

The rule that closes the class (unit-pinned in `VelopackRegistrationGuardTests`): an app running from the per-machine layout - a filesystem fact, no registry consulted - never builds `UpdateManager`; the app log shows `[Update] UpdateManager stays un-built: ... per-machine (MSI) layout ...`. Consequence: installed machines have no in-app update flow (no title-bar card, no auto-check); **updates on installed machines arrive by running a new Setup.msi** - the thin-MSI layout's real update mechanism. Portable/dev layouts keep the full Velopack flow; their per-user root has no MSI registration for a repair to destroy. Do not "improve" this guard into a registry-view condition again: a v1 guard on `MsiEnumProductsW` and a v2 guard on the ARP view each passed its own machine state and each shipped the death from the opposite side.

### A removal sweep must never /x the install it is running from

`EngineInstaller.SweepStaleUserRegistrations` enumerates MSI products named "Uniwill Control Utility" and runs `msiexec /x` on each whose `InstalledLocation` is not this layout - its guard against destroying the live install. That guard used to fail toward destruction: `MsiGetProductInfoW` returning non-zero (the blinded view guarded machines are known for - in-process enumeration sees 421 other products and never ours) fell through to the `/x` branch. An unreadable or empty `InstalledLocation` is now treated as live and skipped; a husk left behind costs one sweep pass, a wrong `/x` costs the install. No unit pin: the decision is inline in a P/Invoke-bound loop (the resolver beside it is pinned).

### The Control Panel uninstall: single entry, bound to the shim at pack time

The packed MSI carries the whole Control Panel story INSIDE the package (build\pack.ps1 step 5a, tool build\msi-edit\MsiEdit.cs). Field-verified end-to-end on the guarded box 2026-10-29 (packs p26-p33): Control Panel → Uninstall → complete sweep, no dialogs. The two key facts:

- **The engine's GUID-keyed entry is hidden by the documented mechanism**: the vpk template ships `ARPSYSTEMCOMPONENT=1`, and Windows Installer registers the entry with `SystemComponent=1` (field dump: `SystemComponent=1, WindowsInstaller=1, ModifyPath=MsiExec.exe /X{code}`). appwiz.cpl/Settings hide `SystemComponent=1` entries, so the user is never offered the product-code route; the sentinel's GUID-key probe rule still watches the entry (its `MsiExec` `UninstallString`), and the elevated install pass keeps redirecting it at the shim as a belt.
- **The product's ONE visible entry is the vpk-published one** (component `ArpRegistration`, KeyPath = the uninstall subkey, so Windows Installer creates the entry on install and deletes the whole key on removal - husk-free by construction). The pack step RENAMES the vpk key (`MSI:Uniwill-Control-Utility`) to the documented convention **`MSI:{product-code}`** - the real code, read from the Property table - rebinds `UninstallString`/`QuietUninstallString` to `"[INSTALLFOLDER]Uninstall.exe"` (the complete-sweep shim), and adds `UCUProductCode = [ProductCode]` plus Help/URL metadata rows. Identity for the sentinel and the shim is the entry's CONTENT (our DisplayName + GUID-shaped `UCUProductCode`), never the key name.

Why the key name must BE the code (field-proven 2026-10-29, both alternatives produced the same appwiz dialog "An error occurred while trying to uninstall ... It may have already been uninstalled. Would you like to remove ... from the Programs and Features list?" - Yes deletes the entry, the product stays installed): appwiz routes an entry to the Windows Installer APIs by PRODUCT CODE whenever the entry carries `WindowsInstaller=1` - and the ARP anti-hijack enforcer on guarded boxes re-adds that value into Control Panel's VIEW of the entry (the true registry shows it absent in an elevated scan, the dialog still routes by code, so the key name cannot be dodged, it must satisfy the rule). vpk's `MSI:<app-name>` key hits the rule directly (prefix convention); the renamed PLAIN key hits it through the enforcer's re-add. With name = real code, both routes complete: the product-code route resolves (genuine MSI uninstall → sentinel SYSTEM sweep), the shell route (clean boxes, no `WindowsInstaller` value) ignores the name and shell-executes the requireAdministrator shim - UAC consent, complete sweep. The dialog is structurally gone.

The `[INSTALLFOLDER]` expansion (field-proven): it expands to the layout ROOT (where vpk's Update.exe lives), while the MSI ships the shim inside the app dir (current\, packed from publishDir) - the authored target file does not exist, and a shell-execute of a missing file is the same appwiz dialog. The engine install pass closes this: `EnsureShimAtPublishedArpTarget` places the layout shim at the published entry's target (content-identified entry, path inside the engine's own layout tree, pure resolver unit-tested in `ShimPlacementTargetTests`), and the shim discovers its verb exe in both layouts (`Service\` dev, `current\Service\` per-machine).

Values authored into the package at build time mean no runtime registry writer, so the ARP anti-hijack enforcer class never applies to the binding - the 22:13 fight (the runtime redirect's `WindowsInstaller` deletion reverted within a minute) is moot: the binding is no longer a runtime write. The runtime `RepairControlPanelUninstall` pass stays as the belt for dev layouts and hand-installed packages, and the sentinel + evidence floor stay the net for scripted `msiexec /x` routes (scripts, GPO, and the hidden GUID entry's product-code machinery).

Product-code transport (guarded-box signature, 22:37 field): the Windows Installer registration tree is PHANTOM to in-process readers - `MsiEnumProductsW` enumerates 421 other products and never ours, elevated included - while the MsiInstaller event stream shows the registration succeeding (msiserver writes are the ground truth, invisible to the blinding). The published ARP entry stays visible, so the shim and the sentinel read the code from the `UCUProductCode` row first; GUID-key ARP (pre-suppression packs) and the enumeration (ARP-blind views) are the ordered fallbacks. The sentinel's registration probe counts the published entry (our DisplayName + GUID-shaped `UCUProductCode`, non-GUID key) as the live machine registration; its component lifecycle makes the probe vanish exactly when the product does.

### Staging a pack on the guarded box (dev workflow)

The full MSI cycle is the ONLY valid staging (field-proven 2026-10-29: a robocopy-patched layout broke launches; the cycle fixed it):

1. `sc stop UCUEngine` → `sc delete UCUEngine` → `taskkill /f /im "Uniwill Control Utility Engine.exe"` (the guarded keep-running policy relaunches the service between stop and delete; killing the live image completes the pending delete - the same trick `UninstallAsync` uses).
2. `cmd /c "msiexec /x {code} /qn"` then `cmd /c "msiexec /i <msi> /qn"` - **raw line through cmd**: a bare `{GUID}` argument in PowerShell is a script-block literal (braces swallowed → msiexec usage pop-ups on the user's desktop, rc=128 = the verb never ran), and a quoted `"/x"` token is an unrecognized option (usage pop-up again).
3. `"...current\Service\Uniwill Control Utility Engine.exe" --install-engine` - registers the service and runs the ARP belt (shim placement + redirect).
4. Update the staged product-code note (`msi-edit inspect` prints `ProductCode =`); vpk changes it per pack.

Never robocopy-patch the layout to stage a new payload: MSI-written files carry the System-IL mandatory label (SYSTEM writes on guarded boxes) plus SYSTEM ownership; an admin robocopy payload is unlabelled/BA-owned. The mixed-label layout parks the ROOT-STUB launch path (the user's double-click) with the app process frozen at ~2 MB, 1 thread, 0 handles, 0 CPU - while direct launches of `current\...exe` (any elevation) run fully. That elevation/route split is the diagnostic signature; the remedy is the MSI cycle, not a patch. A scripted `/x` on this box is thin ("Removal completed successfully, nothing happened"): sweep leftover ARP husks by key with `reg delete`; the sentinel's net needs the app running, so scripted uninstalls do not exercise the full sweep. `mt.exe` stamping of a fresh Setup.exe can hit a transient AV lock (`c101008d`) - pack.ps1 step 5b retries it bounded.

**Standing rule (user-directed 2026-10-31): whenever a change needs field testing, the agent repacks the latest tree and runs this full cycle itself, then hands over the validation gates.** The user starts the app and reports what the gates show; GitHub push/tag/release stays the user's. Mechanics proven in the same-day run (0.9.7 + U-109, product code `{CDFBD405-A8DD-4946-A147-1CDB673EDF94}`):

- **Repacking the same version**: `vpk pack` refuses when `Releases\` holds a release equal-or-greater (the GitHub feed 404s for the private repo, so the local dir IS the feed). Archive the superseded pack's outputs (`*-full.nupkg`, `*-delta.nupkg`, `*.zip`, `Setup.exe`, `win.msi`, `RELEASES`, `assets.win.json`, `releases.win.json`) into `Releases\archive-superseded-<ver>-<date>\`, KEEP the previous-version full nupkg as the delta base, re-run pack.ps1 - the delta rebuilds from it (observed: 18 files patched, 216 unchanged).
- **Equal-version deploy skip (field-proven 2026-10-31)**: a thin scripted `/x` leaves the layout files, and a same-version `/i` over them is a registration-only install - the verbose log shows `File: ...; Won't Overwrite; Won't patch; Existing file is of an equal version` for every payload file, MSI exits 0/1641 "completed successfully", and the NEW package runs the OLD binaries (the tell: the fixed assembly keeps its old timestamp; only a changed-payload delta would be invisible here). Remedy: run `/x {the code the /i just registered}` again - that registration owns the existing components, so the second `/x` removes them fully - then `/i` deploys cleanly (verify the payload timestamps, not just the exit code).
- **Step 1 racing**: the first `sc delete` after `sc stop` can silently no-op (policy relaunches in the gap; `sc query` then shows STOPPED with exit 1067 and the OLD DACL - a pre-grant descriptor like `A;;KR;;;AU`, exactly the stale-DACL state section "The engine service is running yet..." warns about). With the image killed, `sc delete` succeeds and `sc query` must answer 1060 before touching msiexec.
- **msiexec from PowerShell**: drive it with `Start-Process msiexec -ArgumentList '/x','{code}','/qn','/l*v','<log>' -Wait -PassThru` - `/qn` returns instantly without `-Wait`, and the exit code is the verdict. The old product code (from the staged-code note) is the one for `/x`; the fresh MSI's code (from `msi-edit inspect` after packing) goes INTO the note, and the thin `/x` leaves the old-key ARP husk for `reg delete`.
- **Step 3 by app chain**: skipping the manual `--install-engine` verb is fine - the app's post-startup chain registers the service (one UAC prompt on first launch, fresh registration carries the current DACL).
- **Step 3 IS part of the agent cycle (user-directed 2026-10-31)**: run `"...current\Service\Uniwill Control Utility Engine.exe" --install-engine` from the elevated staging shell after `/i`, then verify `sc query` = RUNNING - the user's first app launch is then clean (no UAC). Expect `sc sdshow` to read `A;;KR;;;AU` (not the `A;;CCSWRPRC;;;AU` template) on this box: the service-protection enforcer (observed: Emsisoft) reverts the AU grant every install/re-assert pass (log: 10 re-assert attempts, "DACL did not converge", SACL fingerprint `S:(AU;FA;...;;;WD)`) - with the service RUNNING that costs the user nothing; when the service is NOT running, the unelevated app cannot start it and the elevated repair path pops a UAC **every launch** (the documented classic symptom). The permanent fixes are the AV application allowlist for both images and Authenticode signing (section "The engine service is running yet..."), not the staging cycle.

### CPU power is capped on battery (and a higher request makes it worse)

Field-measured 2026-11-02 on the tester laptop: on battery the firmware caps CPU package power at the Office envelope (~40 W). Selecting a Custom preset with 160 W PL1 did not raise it - actual package power **dropped to 30 W**, i.e. the firmware penalises the request. open-revo documents the same trap for its own platform ("High-performance Custom Mode may trigger instant throttling").

UCU therefore clamps the CPU PL pair to the Office envelope while on DC (`UCU.Core.Power.BatteryPowerPolicy`, Office values from the resolved SKU profile, 45/45 fallback) and says so in a toast; GPU/DB/fan settings are not clamped. On AC the request passes through unchanged. If a future chassis proves a battery-safe override exists, it becomes an evidenced capability, not a UI checkbox.

**Fan control on battery is intentionally unaffected** - nothing is disabled, and the fan page is independent of presets. Note the split/unified semantics behind the "one fan moved first" reports: with split curves each fan follows its own temperature (an idle GPU keeps the GPU fan low while the CPU is stressed), and Unified drives both from the shared source. `EcEngine.ApplyFanCurve` now reads both duty tables back after a write and re-writes once if the EC kept the old table (log: `[WRN] EcEngine: <CPU|GPU> fan table did not land ... re-writing once`).

### "Full Speed" left the fans at about 25 % (fixed)

The preset used to raise the curve duties to 100 % and stop there, but the EC picks the curve zone from the **temperature** first, and zone 0 is the zero-RPM standby step the firmware pins to 0 duty. At idle (45 C) that is the zone in force, so the fans stayed at their floor (~50/200 on the dev box) while the UI said Full Speed. The 2026-11-02 measurement is unambiguous: tables at 200 with `0x0751 = 0x00` -> duty 50/0; writing `0x0751 |= 0x40` (the EC's hardware FanBoost bit) -> 200/200 at the same temperatures, and the duty tables were not touched.

`EcEngine.ApplyFanCurve` now asserts `MANUAL_FAN_CTRL` bit 6 whenever the curve name is `Full Speed`, and clears it for every other preset (that clearing is what the code already did unconditionally). Read-modify-write, so the performance-mode bits the firmware set survive. Regression pins: `UCU.Hardware.Tests/EcEngineFullSpeedBoostTests.cs`.

This also explains the older "one fan moved first" confusion: it was never a dropped write - the tables land (they are read back byte-for-byte), the *zone* just decides whether they matter.

### Every SMU command failed with "Command 'x' not found" (fixed)

Field 2026-11-02 (XMG Neo 16, Ryzen 9 9955HX3D): applying Turbo produced 16 `set-coper` stack traces per apply, plus `slow-limit`/`fast-limit`/`tctl-temp`, and no Core Optimizer or SMU power value ever reached the hardware.

The engine's SMU table was empty: `[AmdSmu] tables configured, 0 commands registered (FireRange gate: false)`. The gate parsed the family/model pair out of the **brand string**, which only carries that shape when Windows falls back to a generic processor name - a machine that resolves a real name ("AMD Ryzen 9 9955HX3D 16-Core Processor") has no "Family"/"Model" words there, so the parse failed and no addresses were registered. The pair lives in the same registry key's `Identifier` value ("AMD64 Family 26 Model 68 Stepping 0"); `CpuModelDetection` now reads that first and keeps the brand string as the fallback. Pins: `CpuModelDetectionTests`.

Log noise is bounded independently: `RyzenAdj_To_UCU.LogCommandFailureOnce` keeps one stack per command name per process and drops repeats to Debug, so a genuinely unsupported command costs one line instead of one per core.

### Battery envelope, measured (CPU and GPU, both laptops)

With a CPU stress test and a GPU benchmark running together, on battery:

| laptop | CPU package | GPU |
|---|---|---|
| Intel Core Ultra 9 275HX | 30-40 W | 35 W |
| AMD (XMG Neo 16, Ryzen + RTX) | 30-40 W | 40 W |

The firmware enforces those, not the request: a Custom preset asking for 115 W GPU sat at ~30 W, and asking for 160 W CPU *lowered* package power to 30 W (open-revo documents the same trap). So `UCU.Core.Power.BatteryPowerPolicy` carries the two envelopes (plus a conservative fallback for unknown chassis) and the app clamps its own requests to them on DC:

- CPU, AMD EC path and the Intel `--intel-pl` path: clamp the PL pair to the envelope's CPU ceiling.
- GPU (`NvTuning.SetPowerLimit`, the single TGP apply site on both platforms): clamp TGP to the GPU ceiling and set Dynamic Boost to 0 - it cannot be borrowed on battery either.
- One toast on a clamp: "On battery, power is limited to the platform envelope (CPU N W, GPU M W)." plus a `[Power] battery envelope:` log line naming requested vs applied.

Undervolt, clock offsets and fan curves are untouched: the firmware clamps power only, and undervolting is the one tuning that still pays off on DC. Presets are therefore *not* disabled on battery, and no second set of battery slots exists - the clamp makes the numbers honest without duplicating the preset model.
Who wins an AC/DC edge: the Automations page's per-edge preset when that edge has one selected (`EnableAutoNavigation` **and** the edge's combo not `None`), otherwise the app re-applies the active Custom preset so the clamp lands. Gating on the master switch alone was wrong - automation enabled with both combos on "None" is the common configuration, and it silently disabled the re-apply.

The clamp is applied when a preset is applied, so the Presets page status card shows the effective pair while on battery ("160 W -> 40 W", "+25 W -> Off") instead of the AC numbers, and a `PowerModeChanged` edge re-applies the active Custom preset so unplugging (or plugging back in) takes effect without touching the UI. That re-apply yields to the user's own AC/DC automation (`EnableAutoNavigation`) and never runs for stock presets, which the firmware owns.

### Every preset is re-applied at startup ("Apply on startup" is gone)

The Presets page carried an "Apply on startup" checkbox that only affected Custom presets (stock presets always applied). Leaving it off meant a relaunch could show the saved preset as active while the EC still held the previous session's values - the state that made the fan page lock itself under a Custom preset on 2026-11-02, and that makes any post-relaunch fan/power report ambiguous.

`MainWindow.ApplyOnStart` now applies whatever preset is saved - stock or Custom - on every launch, and `Settings.ApplyOnStart` is deleted (property and stored value; a user.config that still carries the key is simply ignored). The checkbox and its "Apply on startup" catalog entry are gone (26 catalogs, byte-faithful line removal, 0 insertions). Pin: `FanStartupOwnershipTests.StartupPresetApplyIsUnconditional`.

Consequence worth knowing: a Custom preset's power limits, fan curve and GPU settings are written on every launch, so a machine whose EC firmware clamps something (see the battery section) will look exactly the same after a relaunch as it did before it - which is the point.

### The installer closes the app itself (2026-11-03)

`build\msi-edit\MsiEdit.cs` now authors four more CustomActions into every packed MSI, sequenced **before `InstallValidate`** (1350-1353) so the file-in-use detection never sees a locked image:

| CA | Type | What it runs |
|---|---|---|
| `UcuSetTaskkillPath` | 51 | `UcuTaskkillExe` = `[SystemFolder]taskkill.exe` |
| `UcuSetScPath` | 51 | `UcuScExe` = `[SystemFolder]sc.exe` |
| `UcuStopEngine` | 114 | `sc stop UCUEngine` |
| `UcuKillEngine` | 114 | `taskkill /f /im "…Engine.exe"` |
| `UcuCloseApp` | 114 | `taskkill /f /im "Uniwill Control Utility.exe" /t` |

Type 50 runs an exe whose path comes from a property, so no helper binary and no Binary table travel with the package. The `+64` continue flag is load-bearing: a fresh install has no service (`sc` exits 1060) and nothing to kill (`taskkill` exits 128), and without it the first install died with **error 1722 at UcuStopEngine** - field-proven on 2026-11-03, caught on the first test. The engine is stopped **and killed** before the app, because `AppSupervision` relaunches a killed app: killing the app first just brings it back.

Both paths verified on the dev box with the packed MSI: fresh install with neither service nor app (exit 0, service created), and a forced reinstall (`REINSTALL=ALL REINSTALLMODE=vomus`) while app + engine were running (exit 0, app gone, engine restarted by `UcuEngineInstallDeferred`). `build\pack.ps1` asserts the `114` rows exist after packing.

Registration note: every pack carries a new product code with the same version, so installing a new pack **over** an old one leaves two ARP entries. The documented flow - uninstall the old pack first - is still the rule; the installer only guarantees that the files themselves are never installed under a running exe.
### Never install over a running app (mixed build = the app half-works)

Field 2026-11-02 (tester laptop): the MSI was installed while UCU was running. Windows cannot replace a running image, so the **old exe stayed** while the new `UCU.Core.dll` landed beside it, and every preset apply died with:

```
[Arbiter] Preset intent "BootRestore":'Office' failed to apply
System.MissingMethodException: Method not found: 'Verdict BatteryPowerPolicy.ClampForBattery(...)'
```

The session then ran on whatever the previous one left: the saved Full Speed fan curve applied (with the FanBoost bit), the fan page showed a curve that was not the preset's, and the lock said a stock preset owned the fans. A MissingMethodException is the signature of this state, not of a logic bug.

Two guards now: `App.IsInstallationConsistent()` touches the newest cross-assembly API at startup and, on `MissingMethodException`/`TypeLoadException`/`FileLoadException`, shows "This installation mixes files from different builds…" and exits instead of half working. The install rule stands: **close UCU (and let the engine stop) before running the MSI** - the staging cycle in this document does exactly that.

### Power-edge presets and the locked fan page: what the UI now says

Two field-driven corrections (2026-11-02).

**Automations, power edges.** The controls used to read "Preset / None" as if they were a power switch. On battery the firmware owns the ceilings and the app clamps to the measured envelope regardless, so a power-edge preset now only decides fan noise and who controls the fans (the caption names those two, not undervolt - undervolting is an AMD-only control and the row exists on both platforms). The rows read "Preset on battery" / "Preset when plugged in" with a caption saying power limits stay capped either way, and the leading item reads "Keep current preset" while still persisting `None` (the value `WatcherHubService` and the MainWindow automation gate compare against - the display text lives in a `Tag`, so no saved selection is re-mapped).

**Fan page, locked state.** With a stock preset applied the page is locked because the firmware drives the fans, but it used to keep displaying the user's saved curve - "Full speed" under an applied Office - so the page claimed a curve the hardware was not running. The whole curve area is now collapsed behind a notice that names the active preset ("Office preset is driving the fans", "{0} preset is driving the fans" in the catalogs) and says the saved curve returns with a Custom preset. The Fan Turbo toggle is disabled by the same lock and now reflects the EC's real turbo state on load (`IFanCapability.GetStatusAsync().TurboActive`) instead of an unset local default; both toggle handlers early-return while the page is syncing.

### The fan page locked itself under a Custom preset (fixed)

Field 2026-11-02: Custom preset 1 applied, unplug, close, relaunch - the preset was still applied, but the Fan Control page showed the "Stock Preset Active" lockdown captioned **"Custom preset applied - fan control customization is only possible with a Custom preset."**

The lock (`DeviceApplier.SyncManualControlLock`) was derived from the EC's custom-profile bit (0x0727 bit6). That bit is a **GPU-power-control prerequisite, not a fan-ownership signal**: a custom fan table applies with it clear - measured on the dev box, `0x0727 = 0x00` and a Full Speed apply still took both fans to 200/200 (RPM 4607). Any Custom preset that never activated GPU power control (on battery, or a preset without GPU changes) therefore locked its own fan page, and the overlay's caption - which interpolates the active preset name - contradicted itself.

The lock now follows the app's ownership decision: `PresetProfileApplier.IsBuiltInProfile(presetProfile)` engages it, a Custom preset releases it, and both transitions log (`[Fan] manual control lock engaged/released (preset '...')`) so the field can see which side of the decision a machine is on. Pins: `Uniwill Control Utility.Tests/Services/FanLockOwnershipTests.cs`.

### GPU power reading flapped to absurd values on the Intel laptop (fixed)

Field report 2026-11-02 (PCSpecialist Recoil 3, Core Ultra 9 275HX): on battery, changing the fan curve made the GPU power readout alternate between 22 W and 190286 W, repeatedly. HWiNFO stayed sane, so it is ours.

Cause: on battery the powered-down dGPU reports 0 load, so the GPU row falls back to the **Intel iGPU**. LibreHardwareMonitor's iGPU "GPU Power" is an MSR RAPL energy-counter derivative with an unchecked 32-bit subtraction, and its PawnIO wrapper reports a failed ioctl as a *successful read of 0*. One dropped read therefore yields (2^32 - last)/dt - about 10^5 W for a second or two. 190286 W is arithmetically that wrap at ~1 s cadence; the value is display-only (nothing computes with it), but it broke the fixed-width RTSS column and looked alarming.

`HardwareMonitoringService.PlausibleGpuPowerWatts` now drops anything above 600 W to 0 ("--"), and warns once a minute with the hardware name and the raw value (`[LHM] Rejected GPU power ...`). Pins: `Uniwill Control Utility.Tests/Services/GpuPowerPlausibilityTests.cs`. The same RAPL-underflow shape exists for the Intel CPU package power sensor in that library; if a CPU-watt spike is ever reported, the same guard slots in beside it.

### A stock preset applied at startup, but the fans ran the saved curve (fixed)

Field 2026-11-02 (same box, right after an MSI install): launch showed "Office applied", the Fan Control page was locked, yet the fans ran the previously saved **Full Speed** curve until the Office preset was re-applied by hand.

Cause is an ordering race with a definite loser. `App.ApplyStartupSettingsAsync` runs the power-preset apply (`MainWindow.ApplyOnStart`) and the saved-fan-curve apply (`MainWindow.ApplyEcSettingsOnStart`) **in parallel**, and a stock preset hands the fans to the firmware (`ApplyOemStockMode` clears the custom-profile bit, `0x0751` gets the mode's own profile byte, and the fan page locks itself). Whether the user's curve overrode the preset therefore depended on which write landed last - the engine log shows the stock-mode assertion and then, two seconds later, `Applied fan curves - CPU 'Off'`.

`ApplyEcSettingsOnStart` now skips the fan apply (and the Smart Fan start) whenever `PresetProfileApplier.IsBuiltInProfile(presetProfile)` is true, logging `fan curve auto-apply skipped - the stock preset owns the fans`. Custom presets are unaffected: they carry their own fan settings and are still applied. Pin: `Uniwill Control Utility.Tests/Services/FanStartupOwnershipTests.cs`.

### The "OEM Control Center running" chip on a machine where it is not running (fixed)

Field 2026-11-02 (tester laptop): GCUBridge installed but stopped, Control Center not running, and the title-bar chip still claimed the OEM stack was running. "Pause stack" then answered "Nothing to pause", and the only way out was "Not now" (session-only dismissal, so it returns next launch).

The two decisions used different truths. `OemTakeoverService.ShouldWarn` asked for `ServicesInstalled > 0` plus state `Active`/`PartiallyPaused`, and `TakeoverPolicy.DecideState` returns `Active` for "installed, nothing live, no pause evidence" - a fallback, not a liveness test. The pause path counts **mutations**: a stopped demand-start service with no live process and no enabled task produces zero, hence the toast.

`ShouldWarn` now also requires live evidence (`ServicesRunning > 0 || OemProcessesRunning > 0`), which is what the chip's own text says and what guarantees the Pause button has something to do. An installed-but-idle stack no longer warns; it still shows in Settings with its own state. Pins: `OemWarningTests.Silent_WhenTheStackIsInstalledButNothingIsRunning` and `Warns_WhenOnlyAnOemProcessIsLive`. If product ever wants a "the OEM stack will fight you after the next reboot" pre-warning, that is a separate, explicit message - it must not be this chip.

### Display brightness is missing

Display → **Display brightness** (U-205) writes through the panel's WDDM brightness control (`root\WMI` → `WmiMonitorBrightnessMethods.WmiSetBrightness`), then re-reads `WmiMonitorBrightness.CurrentBrightness` as the evidence — the row is hidden entirely when the panel exposes no such class, so a missing slider means "this display has no WDDM brightness control", not a bug (external monitors are handled by their own DDC/CI controls, not by this row). The warning `[Display] brightness write to N% did not verify` means the panel accepted the call but reports a different value (driver clamp); the label then shows the readback, never the request.

**Screen off was removed** (2026-11-01). The implemented form - broadcasting `WM_SYSCOMMAND`/`SC_MONITORPOWER` to every top-level window - put the test machine into a sleep loop that only a forced power-off cleared: on modern-standby systems the broadcast is not a display-only request. Do not reintroduce it in that shape; anything display-power related must be scoped to the app's own window (or left to Windows' own power settings).

### An imported ICC profile is refused (or does not show up)

Display → Color Calibration now imports the user's own `.icc/.icm` files and exports the associated one (U-205). Import is gated by `UCU.Core\Display\IccProfileValidator`: the header size must match the file, offset 36 must carry `acsp`, the major version must be 2–4, and the tag table must fit inside the declared size. A file that fails any clause is refused with the reason in the toast and **nothing is associated** — Windows would happily accept the association for a non-profile and render the panel through a broken transform.

Imported profiles are copied to `%LOCALAPPDATA%\UCU\icc` (per-user: the spool folder needs administrator rights) and then join the combo, where association uses the existing `InstallColorProfile` + `WcsSetDefaultColorProfile` path. Export copies the currently associated file out — useful to move a calibration between machines. A profile imported on one Windows account is not visible in another, by design.

### Keyboard shortcuts do not fire

Shortcuts are user-editable under **Automations → Keyboard shortcuts** and persist in `%LOCALAPPDATA%\UCU\shortcuts.json` (the record is the file; an unreadable file is moved to `.bak` and the map starts empty). Three facts make most "my shortcut does nothing" reports self-diagnosing:

- **At least one of Ctrl, Alt or Shift is required**, and only one primary key. A modifier-only chord is rejected on save; a hand-edited row that fails the grammar is dropped on load (the hook never fires a bad row).
- **The chord is matched by the same global hook as the overlay toggles**, and that hook is installed while the overlay is enabled **or** at least one shortcut exists - a shortcut set does not die with the overlay toggle. The hook still runs on its dedicated pumped thread regardless of which consumer asked for it.
- **One action per press**, the whitelist being the watcher hub's class: apply preset (through the preset arbiter, same priority as a tray click), set performance mode, enable fan turbo (set semantics - it does not toggle off), pause/restore the OEM Control Center. Presets apply with the usual toast; takeover actions carry the same outcome lines as the Settings card.

A shortcut that fires the wrong thing is a duplicate chord: the first row wins on load, and the editor's saved file keeps one binding per chord.

### OEM Control Center takeover (pause/restore)

Field context for story U-203 (Settings → "OEM Control Center" card). The OEM stack (`GCUBridge`/`GCUService`, the ControlCenter tray/services, its scheduled tasks and Run keys) re-arms the OEM fan curves, so it fights UCU's fan/power writes; the takeover pauses it (journal-first, fully reversible) and restores it untouched.

- **The stack lives on the tester laptops, not on the dev box.** The 2026-11-01 probe proved the dev box has zero catalog services/tasks/Run-key entries, so the dev-box gate is the auto-bypass: `oem.get_status` answers `NotInstalled`, and pause/restore apply zero mutations (the reference's Thin & Light path — a machine without the stack is a clean answer, never an error).
- **The hardening gate is why a pause can report fewer mutations than the catalog.** A target mutates only when the name matches AND, for a file-identity target, the image path exists AND the signature chain validates (WinVerifyTrust, offline) AND the publisher CN carries an allowlist keyword (uniwill, mechrevo, xmg, aistone, gcu, control center, gaming center, pcspecialist, tongfang). Refusals appear in the card's red suspects line and are never touched. The self-guard is field-necessary, not theoretical: on the dev box the ONLY "uniwill" process/Run-key match is UCU itself.
- **Publisher evidence is the WinTrust signer walk, not a certificate-file read** (field-proven 2026-11-01, pack #23 tester-laptop round: the card refused the whole real stack as `publisher '' is not on the OEM allowlist`). `WinVerifyTrust` answers "chain trusted?" but not "signed by whom"; the subject comes from the VERIFY provider state (`WTHelperProvDataFromStateData` → `WTHelperGetProvSignerFromChain` → the leaf `CERT_INFO.Subject` → `CertNameToStrW`). A certificate-FILE loader cannot read a PE's embedded signature (it throws, the gate saw an empty subject, every OEM binary was refused), and `X509Certificate.CreateFromSignedFile` is SYSLIB0057-obsolete.
- **Two identity exemptions keep the gate from refusing OEM targets that are correctly built.** (1) *System binaries*: inbox EXEs are catalog-signed (no embedded Authenticode) — `notepad.exe` itself answers `TRUST_E_NOSIGNATURE (0x800B0100)` to `WinVerifyTrust(CHFile)`; a task whose actions are all under `System32` (field case: the OEM `ControlCenter` task runs `powershell.exe -File <script>`) is exempt, because a user cannot plant a System32 image. (2) *MSIX package payloads*: the UWP Control Center's Win32 helpers live under `WindowsApps\ControlCenter3_*` and carry the AppX package signature, never per-file Authenticode (field case: `SystrayComponent` read as unsigned); the packages tree is writable only through package identity, so the path + catalog name is the whole identity — the same squat-immunity the policy documents for the registry-byte scopes.
- **`UWACPIDriver.sys` is NOT a takeover target** — it is UCU's own driver; pausing the OEM stack must never unload the EC transport.
- **Discoverability: the title-bar chip.** While the stack is live (state `Active` / `PartiallyPaused`) the title bar shows a caution-colored **"OEM Control Center running"** chip; clicking it opens a small review popup (status line, `Pause stack`, `Open Settings`, `Not now`). The chip is the answer to "the Settings card is too hidden to matter": a user who never opens Settings would otherwise never learn why fan settings "don't stick". `Not now` dismisses it for the session (the next launch re-checks, so a stack that came back after a reboot is warned again); a successful pause removes it naturally. The probe is throttled (60 s) — the chip is a status indicator, not a live meter.
- The journal is two files (`%ProgramData%\UCU\engine\oem-takeover-journal.json` machine scope, `%LOCALAPPDATA%\UCU\oem-takeover-journal.json` user scope) merged newest-first in the card. "Paused" means the journal has entries and nothing catalog-named is running; restore consumes exactly the entries it reversed, so the list drains to empty as the state returns to `Active`. A journal that survives an OEM uninstall surfaces as `Stale` — restore consumes its entries (targets report "gone").
- **Restore restores the pre-pause state, it does not start the stack.** A service that was RUNNING at pause time carries the `|running` flag and is started again; a service that was already stopped before the pause is only re-armed (its `Start` value is restored, and an `auto` one returns at the next boot). Field-reported 2026-11-01: GCUBridge "off before installing UCU" then paused/restored stayed off — that is the documented behaviour, not a defect. The action line `service <name> was running before the kill pass` marks the cases where the process kill (first in the pause order) stopped the service, and is what guarantees the start happens on restore.
- **Open field item (tester laptop):** capture the exact publisher CNs of the real OEM binaries (the allowlist is keyword-based until the CN capture lands) and run one pause → reboot → restore round-trip; the restore order (bridge first, spawned service watched, rest started) targets the reference's watchdog cascade.

### Power Tuning Guardian (power-limit drift healing)

The guardian (Automations → Power Tuning Guardian) is opt-in per feature, **off by default**: each enabled half periodically reads the EC's power-contract truth (`power.get_contract_truth` — the GPU cTGP/DB bytes `0x0743`/`0x0744`/`0x0745`/`0x0746`, the custom-profile bit `0x0727!bit6`, and the CPU PL pair `0x0783`/`0x0784`; laptop NVML answers NOT_SUPPORTED for power limits, so the EC registers are the only truth) and re-applies the contract the preset pipeline last applied when a third-party tuner reset it. The app log (`%LOCALAPPDATA%\UCU\logs`) carries the full evidence trail, all prefixed `[PowerGuardian]`:

- `contract loaded/noted/cleared …` — what the guardian believes the contract is; a stock preset apply **clears** it (the firmware's factory table rules, nothing to heal).
- `drift detected: gpu=… cpu=…` — the moved register bytes (hex) / wattages before the heal, and `contract restored, verified by EC re-read` after it. The user toast fires only on that verified path, throttled to one per 10 minutes.
- `engine not answering (Busy/Timeout/HardwareUnavailable) - backing off` — normal under engine load; the guardian pauses 60 s, it never queues onto a saturated power domain.
- `heal refused: InvalidValue …` — the contract bytes are no longer valid for this firmware; fix the preset, the guardian does not retry blindly.
- `heal NOT verified: …` — the write landed but the EC re-read still shows the tuner's bytes: something is actively re-tuning (check Afterburner / OEM control center startup entries).

Cycles are silently skipped while Adaptive is running (its diff-apply loop owns tuning), while the GPU driver-transition cooldown is armed (GPU half only), and when the persisted contract (`%LOCALAPPDATA%\UCU\power_contract.json`) is empty.

### Overlay has no FPS value

Confirm RTSS is running and publishing the foreground process. Without RTSS, the ETW fallback must be able to observe present events and resolve the foreground executable. Some protected processes prevent module-path inspection; telemetry may remain unavailable while other overlay metrics continue.

**RTSS "running" with no tray icon: check its session.** `RTSSSharedMemoryV2` is a **global** name, so an RTSS instance living in **session 0** satisfies the app's shared-memory witness (and any "is RTSS running" check that uses it) while the user has no tray icon and no overlay in their games. Field-proven 2026-10-31: a one-shot `Highest`-privileges scheduled task (S4U principal — the pattern that works for launcher-style actions) lands a GUI process in session 0. Diagnose with `Get-Process RTSS | Select-Object Id, SessionId` — the instance must sit in the user's session (console session, usually 1). UCU's prerequisite row and auto-start are session-scoped on purpose and start RTSS **through the engine**, which places it in the active session with the console user's linked (elevated) token — needed because RTSS flagged "Run as administrator" fails a launch against the filtered token (ERROR_ELEVATION_REQUIRED) with no dialog a service could answer. A stale session-0 instance is killed, not adopted: `taskkill /f /pid <id>` (elevated) and let the row's Start bring it back correctly.

Two field observations about the engine-launched instance. It runs at the console user's **linked (elevated) token**, so a module-path read from a filtered token throws (`Get-Process RTSS | Select-Object MainModule` fails while `Id` and `SessionId` work) — that is the high-integrity process behaving normally, not a defect; on machines without RTSS's "Run as administrator" flag the engine route starts RTSS elevated where the user's own double-click starts it filtered. And a start is verified by the process **appearing in the user's session and staying** (a minute is a fair gate) — one dev-box instance vanished ~90 s after a service-launched start with no Application Error event, which is why liveness is the process list, sampled over time, never the shared-memory segment.

## Suspend/resume verification

After changes to hardware state handling, verify this sequence:

1. Apply a custom profile, lighting, battery limit, fan curve, and connected peripheral state.
2. Enter sleep or hibernation.
3. Resume and wait for the delayed reapplication.
4. Confirm the active profile, EC fans, battery mode, keyboard, light bar, Hydro UI, and Flydigi devices.
5. If Adaptive Mode is enabled, start a configured game and confirm every selected domain reapplies once.
6. Exit UCU and confirm Windows releases BLE/HID sessions.

## Recovery and data reset

Prefer backing up first from Settings. To isolate corrupt state, move one owning JSON file out of its directory and restart; the owner will load defaults. Reset `.NET user.config` only after capturing it, because it contains cross-feature preferences and active profile state.

For EC fan-specific recovery, use the automatic-control restoration flow documented in [Uniwill EC fan control](../protocols/uniwill-ec-fan-control.md) rather than manually editing arbitrary registers.
